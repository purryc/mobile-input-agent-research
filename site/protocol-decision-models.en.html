Protocol & decision layer · Research update · 2026-11-17

A2UI 1.0 + Jev:
decide the controls, then build the UI

The opportunity for Mobile Input Agent is to separate choosing useful controls from authorizing the actions behind them.

Official specifications, release notes, model documentation and sample code reviewed. No paid inference, latency replication or live executor integration performed. Design proposals below are not shipped features.

01 · Extend the existing architecture

This adds to the Survey's generative input surfaces and control protocol. Keep target identity, capability checks, request revisions, real receipts and the distinction between stop and undo. A2UI may display these facts; it does not validate execution authority.

Input + state snapshot
target, focus, task, revision
↓
Deterministic capability / policy filter
remove unavailable actions first
↓
Rules OR decision model OR LLM
select a surface, never grant authority
↓
Deterministic builder → A2UI → renderer
allowlisted components and validated values
↓
User action → execution policy → tool
receipt, verification, recovery

Our design proposal. Pointer movement, scrolling and continuous dial input stay in a local low-latency loop, not a cloud-model call per event.

02 · Keep the layers separate

A2UI
Declarative UI messages between an agent and renderer; transport-agnostic, not inherently SSE or A2A.[P2]
Express
Compact model-output format compiled into A2UI JSON; changing it need not change clients.[P4]
Jev / System One
Typed judgments over state, not a new UI protocol.[P7]
Builder / renderer
Code maps choices to valid components; the host displays them. Neither invents execution capabilities.
MCP / application APIs
Permission-bound tool access in this proposal, not the UI decision model.
A2A
A separate agent-interoperation layer, not a prerequisite imposed by this design.

03 · Corrections to the supplied article

  • Stable protocol does not mean simultaneous ecosystem migration.Google announced 1.0 on November 11; the announcement still listed Compose at 0.9.1 and Lynx adapting to 1.0. Pin renderer/catalog versions.[P1]
  • Do not copy legacy message names.1.0 uses createSurface / updateComponents / updateDataModel / deleteSurface, not the article's beginRendering / surfaceUpdate. Bidirectional functions are not arbitrary execution.[P2]
  • Migration is not global search-and-replace.Reserved @path / @call differ from plain fields such as updateDataModel.path. Protocol theme/primaryColor were removed; host themes and custom catalogs still handle styling.[P3]
  • Official Jev inference-format support remains on the roadmap.Custom builders and examples are research paths, not official plug-and-play SDK integration.[P5]
  • Security needs more than a catalog.Allowlisting does not establish correctness or authorization. Server-side macros can reduce model-visible data; proving that sensitive values never reach a model requires inspecting actual data flow.[P6]

04 · What the decision-model evidence supports

Jev exposes Choice, Score and Noul for typed selection, scoring and probability judgments. Batched questions are evaluated independently against the same state. Decompose multi-factor judgments and compose results in code.[P7]

Google's hybrid example selects layout with Jev, constructs it in code, then fills text with an LLM. Its 11-prompt demonstration reported first trees in 92–298 ms and complete responses in 0.8–1.7 s. These are not mobile end-to-end guarantees or evidence for a universal “80×” improvement.[P6]

The Express benchmark used 54 samples. Without thinking, input tokens fell from 10,980 to 6,000 and code tokens from 807 to 297; both formats scored 98.1% pass rate and 97.2% quality. This supports token efficiency, not general quality gains or proportional latency reductions.[P4]

Our interpretation: the transferable idea is finite choices + typed answers + code-enforced constraints. Confidence is neither permission nor a locally calibrated correctness rate. “System One” alone establishes no on-device deployment, privacy guarantee or cost advantage.

05 · Proposed application-level decision contract

This is our architecture sketch, not standard A2UI fields or the Jev API request schema.

State: task_id, target_id, context_revision,
       focused_role, allowed_actions, execution_status
Decide: surface_kind ∈ {fixed, parameters, draft, review, clarify}
        useful_controls ⊆ allowed_controls
Output: typed_choice + uncertainty + context_revision
Build:  allowlisted component tree + data bindings
Act:    target/version/permission checks + receipt
  • Use minimal authorized context. Do not default to collecting full screens, email, clipboard contents or activity history.
  • Rules first for known shortcuts, continuous input and explicit approval flows. Decision models help ambiguous surface selection; LLMs handle open-ended tasks or text.
  • Filter candidates before inference and validate afterward. Reject stale context revisions rather than replacing a newer focused surface.
  • Keep positions stable and pin layout during editing. Recompute on meaningful changes, with debounce, hysteresis and a visible fallback.
  • On uncertainty or conflict, preserve fixed controls, clarify or hand back to desktop without side effects. Calibrate thresholds on project data.
  • Recheck target, revision, scope, expiry and idempotency at execution. A visible button grants no authority; stop cannot imply reversal.

07 · Minimum experiment and migration checks

A/B/C: fixed rules vs LLM+Express vs typed decisions+deterministic builder. Hold catalog, task set, client and network conditions constant. Start with a simulator without real side effects.

  • Measure p50/p95 time to actionable UI and whole-task completion, correct-control selection, abstention coverage, wrong targets, corrections, layout churn and recovery effort.
  • Inject focus changes, stale snapshots, missing capabilities, disconnection, duplicate actions and low confidence while the user edits. Schema validity is not task success.
  • Pin versions; test negotiation, catalog protocolVersion, caller restrictions and user-activation requirements before adopting old samples.[P2][P3]
  • jev2ui is an evolving experiment, not conformance certification. Audit its extensions and dynamic-code paths separately rather than copying them into the production allowlist.[P8]

Recommendation: first test whether finite decisions interrupt less than rules and behave more consistently than free generation. This update is research and architecture, not procurement or implementation.
